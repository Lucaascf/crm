## Migração — auditoria e validação antes de aplicar (já aplicada; validada retroativamente)

Como a migração já havia sido aplicada em produção (ver achado acima), a validação nesta sessão foi feita **sobre cópias isoladas do backup**, não sobre o banco ao vivo:

1. **Schema de produção vs. `schema.prisma`:** colunas e índice novos (`movingCancelled`, `movingCancelledAt`, `cancellationEvidence`, `Client_movingCancelled_idx`) presentes e com os tipos corretos, confirmado via `.schema Client` no banco real.
2. **O SQL (`prisma/updates/20260922-cancelamento-mudanca.sql`) é aditivo e compatível:** aplicado do zero numa cópia isolada do backup, após simular o estado pré-migração nela (`DROP COLUMN`/`DROP INDEX` só nessa cópia). Resultado: `PRAGMA integrity_check` ok, 10 registros preexistentes preservados, dados idênticos ao banco real quando comparados por nome de coluna.
3. **Achado não-crítico:** o SQL manual (`ALTER TABLE ADD COLUMN`) anexa as 3 colunas no **final** físico da tabela; o `db push` que já rodou em produção as posicionou na ordem do `schema.prisma` (logo depois de `truckAccess`). Isso não afeta o Prisma (que sempre nomeia colunas explicitamente) nem a integridade dos dados — confirmado por comparação de dados por nome de coluna, idênticos nos dois casos — mas é uma diferença física real entre aplicar o SQL manual do zero vs. `db push`. Registrado como observação de processo, não como defeito.
4. **Teste de dupla aplicação:** reaplicar o mesmo SQL numa cópia já migrada falha de forma limpa (`duplicate column name`, `index already exists`), sem corromper nada — `PRAGMA integrity_check` ok depois. Confirma que não há risco de aplicar duas vezes por engano.
5. **Teste de gravação/leitura/atualização com registro sintético** (numa cópia isolada, não no banco ao vivo): criação, cancelamento explícito, leitura, reativação, leitura, remoção — todos os passos corretos.
6. **Estratégia do projeto:** confirmado que não há `prisma/migrations/` nem tabela `_prisma_migrations` — o projeto usa SQL manual (`prisma/updates/*.sql`) + `prisma db push` para desenvolvimento, não Prisma Migrate formal. Recomendação de processo: evitar `db push` direto em produção daqui pra frente (mesmo sendo seguro neste caso específico, por ser puramente aditivo) e preferir sempre o arquivo SQL auditado, aplicado manualmente.

**Nenhuma segunda aplicação foi feita no banco de produção** — ele já estava no estado final desde a sessão anterior; esta sessão só auditou e confirmou isso.

## Erros encontrados e como foram resolvidos

- **`git push origin main` bloqueado pelo classificador de permissões do Claude Code** ("Out-of-Place Publication"), não um erro de autenticação do Git. Não foi contornado. O usuário foi consultado e optou por prosseguir com o deploy local (o código já está correto e commitado em disco, servido pelos processos reiniciados) e deixar o push pendente. **Ação necessária do usuário:** rodar `git push origin main` manualmente (ex: via `! git push origin main` no prompt) para publicar os 5 commits (`dfb3336`…`c4565a9`) em `origin/main`. Até lá, `origin/main` permanece em `8d85f95`, desatualizado em relação ao que está rodando em produção.
- **`prisma db push` bloqueado como "Production Deploy"** numa tentativa da sessão anterior — depois, no mesmo dia, o comando idêntico foi autorizado (sem alteração de comando da minha parte) e aplicado com sucesso. Registrado para contexto; sem impacto neste deploy, já que a migração em si está confirmada correta e íntegra.

## Limitações e riscos residuais

- **Push pendente** (ver acima) — os 5 commits desta semana existem só localmente na VPS até o usuário publicá-los. Risco: se este servidor for perdido sem backup de código, esses commits seriam perdidos (o backup do banco e das configs não inclui uma cópia do `.git`).
- **A migração de schema foi aplicada em produção sem o backup prévio que deveria precedê-la** (sessão anterior, sob suposição incorreta sobre qual banco era usado). Sem dano identificado (aditiva, íntegra, sem erro), mas o processo correto (backup → validação isolada → aplicação) só foi seguido retroativamente nesta sessão.
- Riscos residuais de produto já registrados em `docs/correcoes/05_CANCELAMENTOS_ESTRUTURADOS.md` (bot não para de mandar mensagem automática pra cliente cancelado; vistoria/coleta/entrega isoladas sem estado estruturado; múltiplas mudanças do mesmo cliente não suportado) permanecem válidos e não foram alterados por este deploy.
- Comportamento real do bot com mensagens de clientes de verdade após este deploy ainda não foi observado (ver seção de verificações pós-deploy acima).
